## Sprite acquisition

`add-localtanks-tank` consumes a finished `_strip2.png`; it does not create or edit artwork.

1. Run `scripts/find_localtanks_sprite.ps1 -TankName <designation>`.
2. Use one unambiguous existing canonical match only when its manifest records the current client's top chassis, turret and gun.
3. If there is no suitable match, or its manifest contains stock/intermediate modules, load the `render-wot-tank-sprite` skill and follow it without explicit module indices, then use its validated top-configuration output.
4. If several exact variants remain plausible, ask the user to choose. Do not substitute a merely similar vehicle.

The render fallback writes ignored local material. Keep the sprite, layout, manifest, validation images, Blender files, textures and intermediate renders out of Git. Unity imports the canonical sprite directly from `WoTGenerated`; never create a tracked gameplay copy.

- `Assets/Game/Runtime/TankDefinition.cs`: valid vehicle classes, runtime fields and the `TankAudioProfile` field set.
- `Assets/Game/Runtime/ShellDefinition.cs`: shell fields, including the per-shell impact `ShellAudioProfile`.
- `Assets/Game/Runtime/BattleDirector.cs`: spawning and `TankPrefabBinding` resolution.
- `Assets/Game/Runtime/TankAudioController.cs`: how the tank audio profile is loaded and played.
- `Assets/Game/Tests/EditMode/CombatDefinitionTests.cs`: roster, availability and definition-invariant assertions.
- `Assets/Game/Tests/EditMode/BattleScenarioTests.cs`: team size, national homogeneity and scenario validation.

Registry lists are derived from data now: `PrototypeSetup.FindTankPrefabPath` resolves a tank id to its prefab, and `RiverCrossingSetup.CreatePrefabBindings` builds the scene bindings from every playable tank plus every scenario entry. A new tank needs a build spec entry and its JSON definitions only — never a second prefab list, a second tank-id list or a scene edit. `availableInGame` is the single playability switch and decides whether the tank appears in the test range and in the two laboratories; it does not by itself add the tank to the fixed battle roster, which stays hand-authored in `river_crossing_battle.json`.

## Existing data contract

Tank JSON schema version 1 contains:

- `id`, `displayName`, `vehicleClass`, `nation`, `tier`, `availableInGame`, `maxHitPoints`, `weaponId`;
- `mobility`: `maxForwardSpeed`, `maxReverseSpeed`, `acceleration`, `groundResistance`, `braking`, `hullTurnSpeed`, `turretTurnSpeed`;
- `armor`: `front`, `left`, `right`, `rear`;
- `vision`: `stationaryConcealment`, `movementRevealPenalty`, `firingRevealPenalty`, `firingRevealDuration`. Never author `viewRange` or `guaranteedDetectionRange`: the importer derives both from `vehicleClass`, `tier` and `VisionRangeTable` and rejects those field names in a tank JSON.
- `audio` for every available tank. The validated field set is broader than engine/shot/turret: `engineClipId`, `tracksClipId`, `shotClipId`, `reloadClipId`, `turretClipId`, `destructionClipId`, plus `engineVolume`, `tracksVolume`, `shotVolume`, `reloadVolume`, `turretVolume`, `destructionVolume` (0..1) and `enginePitch`, `tracksPitch`, `shotPitch`, `reloadPitch`, `turretPitch`, `destructionPitch` (0.25..3). The validator rejects a definition whose present `audio` block has an empty clip ID or an out-of-range number, so supply every field.

Valid vehicle classes are `HeavyTank`, `MediumTank`, `LightTank`, `TankDestroyer`, and `Artillery`. Current nations are `Germany`, `USSR` and `USA`; always inspect the live enum before adding another. `tier` is the official WoT level of the exact rendered vehicle and must be an integer from 1 through 10. An unavailable definition remains buildable but must stay out of playable scenes and rosters.

Weapon JSON contains `id`, `displayName`, `reloadSeconds`, and `shellId`. Shell JSON contains `damage`, `penetration`, visually scaled `speed`, `radius`, `lifetimeSeconds`, `maximumRange`, and ricochet settings.

Use the live schema/validator if fields change.

## WoT-to-LocalTanks conversion

- Start from the top module configuration in the current WoT client: last/highest chassis, turret and gun plus the highest-power compatible engine. Do not combine stock or intermediate modules with top values. A user-explicit alternate configuration is the only exception and must be documented.
- HP, shell damage, penetration, nominal armor, mass, maximum speed, traverse, reload, aiming, view and concealment use WoT values as their baseline.
- `Rigidbody2D.mass`: WoT tonnes where available.
- Linear speed: never calculate the conversion ad hoc in a tank task. Use the maintained values and conversion in `Tools/WoTDataPipeline`; its current compatibility value is 13.9 km/h per Unity speed unit, while the world geometry uses `GameScale.MetresPerUnit = 3.835`.
- Projectile speed and maximum range: use exactly what the maintained data pipeline writes. The current implementation still uses `projectileSpeedDivisor = 55` and a 40-unit range for readability; ADR-065 has accepted real WoT speed/range, but the migration belongs to Sprint 010 P6 and must not be applied to one vehicle in isolation.
- Armor and penetration: millimetres. Store nominal plate thickness, not line-of-sight effective thickness; runtime incidence angle supplies the geometric multiplier.
- Accuracy/dispersion, view distance and concealment require a documented global mapping into the smaller LocalTanks battlefield. Preserve WoT ordering and relative strengths.
- Acceleration, ground resistance and braking use WoT mobility data where exposed; otherwise derive them from WoT power-to-weight, terrain resistance and class peers and label the derivation.
- A LocalTanks balance adjustment is allowed only after roster comparison and must preserve the raw WoT value, final value and reason in `Docs/TANK_REFERENCE.md`.
- Prototype or paper vehicle: explicitly label what was built, what was proposed, and which configuration the game represents.

## WoT audio profile

Use the dedicated `wot-tank-audio` skill; this is only the integration summary.

- Resolve engine, tracks, main-gun, reload, turret-traversal, impact and destruction events for the same selected modules in the local WoT client.
- Register missing named events once in `Tools/WoTAudioPipeline/audio_clips.json`, then run `Tools/WoTAudioPipeline/Scripts/Invoke-WoTAudioPipeline.ps1`.
- Reuse stable clip IDs in `Assets/LocalOnly/Resources/WoTAudio/Clips`; shared events such as an engine family or gun class must produce one physical WAV.
- Store the mapping and per-vehicle volume/pitch in the tank JSON `audio` object. `TankAudioController` resolves Resources by ID only at runtime, so a committed prefab must not contain a local AudioClip GUID.
- Keep clips, `.meta`, audio manifest, extracted banks, media, TXTP and third-party binaries local and out of Git. Verify with `git check-ignore` and `git ls-files Assets/LocalOnly LocalData`.
- If resolution fails, retain the discovered module/event IDs and report the missing profile. Never substitute a random clip without documenting a deliberate class/caliber fallback.

## Art and prefab measurements

Do not alter the selected sprite. Use the layout sidecar's Unity bottom-left rectangles and turret pivot when present. Without a sidecar, determine non-transparent component bounds rather than guessing slice rectangles and set pivots from visible mechanical centers, not canvas centers. Preserve existing sprite IDs when configuring an already imported tracked texture. Scale the finished hull from a documented real dimension against the established game scale.

### Hull contour contract

The hull geometry is the one part of a build spec that a compiler cannot check, so it has explicit rules and the build enforces all of them by failing with the tank name:

- **Fleet scale.** Never enter a visual scale. The build spec carries the documented real hull length in metres, and `PrototypeSetup.ScaleForHullLength` derives the scale by comparing the machine against the reference tank (Tiger II: 7.38 m, 802 pixels, scale 0.24). This is the only thing that keeps machines correct relative to each other, because a wrongly scaled sprite still matches its own collider perfectly. The T1 Cunningham once came out 77% longer than a Tiger II this way.
- **Units.** Contour points are world units equal to half of the sprite rectangle multiplied by the derived scale. For a hull rectangle of `width` × `height` pixels at scale `s`, the contour spans `width / 100 * s` by `height / 100 * s`, and a half extent is `width / 200 * s`. MS-1 is the reference: ±0.23 × ±0.56. Normalized `-1..1` points or points doubled by mistake produce a collider that does not cover the sprite.
- **Uniform scale.** The derived scale is used on both axes. A mixed scale stretches the sprite away from the collider derived from the same rectangle.
- **Point count.** At least ten points, so the outline keeps the chamfers a box collider would lose.
- **Sprite agreement.** The build measures the drawn hull rectangle against the documented length at 108 pixels per model metre and rejects a disagreement over 8%, which catches a sprite rendered at the wrong scale or a wrong documented length.
- **Enforcement.** `Local Tanks > Build Combat Assets` validates all of the above and logs `collider W x L, sprite W x L, points N, hull L m draws as U units` per tank. `TankPrefabRegistrationTests` re-checks the generated prefabs, including that the fleet scale is shared. Read the build summary first when a hull looks wrong.

Build a 10-16 point convex or appropriately supported polygon outline around the visible hull, with extra points at real shoulders, nose changes, and rear tapers. Keep the outline inside the painted tracks/armor edge so hits match the art. Confirm the forward axis used by movement, turret, and muzzle. The turret ring offset, the muzzle distance and the outline are all computed from the layout and the derived scale, so they follow a corrected length automatically.

The current turreted prefab hierarchy is:

```text
<Prefix>_Player
├── HullVisual
└── TurretPivot (TurretAiming)
    ├── TurretVisual
    └── Muzzle
```

The root currently carries `Rigidbody2D`, `PolygonCollider2D`, `TankMotor`, `WeaponController`, `PlayerTankInput`, `TankHealth`, `TankAudioController`, `TankArmor`, and `TankDestroyedState`. Match current code, not this snapshot, if components change.

## Base-battle roster rules

`river_crossing_battle.json` must retain:

- exactly the current `BattleScenario.TeamSize` entries for Team A at base `A` and Team B at base `B` (currently 7 per side);
- unique spawn slots within each base and the current `BattleScenario.SpawnSlotCount` range;
- exactly one `playerControlled: true` entry, on Team A;
- valid North/Center/South routes and Assault/Support/Flank roles;
- only `availableInGame` definitions whose `nation` matches every other entry on that team;
- a valid prefab binding for every tank ID used by the scenario.

Assign likely roles by class and actual mobility: scouts/flankers to `Flank`, breakthrough heavies to `Assault`, most mediums/TDs/artillery to `Support` unless their design suggests otherwise. Do not alter route geometry solely to add a vehicle.

Add a newly available machine only to its matching national team. When a team is full, replace a duplicate of another vehicle from that same nation while preserving lane counts and roles. Never mirror a machine onto an opposing nation merely for symmetry. Unavailable definitions require no roster coverage.

## Durable tests to add or maintain

Favor invariant tests over ever-growing hardcoded lists:

- discovered tank JSON IDs equal imported database IDs;
- every tank definition has exactly one build/prefab registration;
- every scenario tank ID has a non-null prefab binding;
- every scenario definition is available, bound to a prefab and placed only on a nationally matching team;
- team counts match `BattleScenario.TeamSize`, spawn keys are unique, and exactly one player exists;
- a representative projectile collision damages the new prefab;
- the collider is polygonal and has a meaningful number of points;
- turretless vehicles do not receive unsupported rotating-turret behavior.

## Recommended build order

1. Resolve and inspect an existing sprite; load `render-wot-tank-sprite` and follow it when none exists or its manifest is stale.
2. Add JSON and refresh/import combat definitions.
3. Load `wot-tank-audio` and follow it: resolve or register events, run `Invoke-WoTAudioPipeline.ps1`, add the tank JSON audio mapping.
4. Add the prefab build spec and any generic turretless support.
5. Build the test range/prefabs through `PrototypeSetup.BuildAll` or its current replacement.
6. Update scenario and prefab bindings.
7. Build River Crossing through `RiverCrossingSetup.Build` or its current replacement.
8. Run Edit Mode tests, then targeted Play Mode tests, in batchmode, and inspect the logs.
9. Open the generated base scene and visually inspect the new tank in motion and listen for engine, tracks, turret, reload and shot behavior.
10. Update `Docs/TANK_REFERENCE.md`, `Docs/STATUS.md`, `Docs/CHANGELOG.md` and `Docs/BACKLOG.md`, then commit only scoped tracked files.
